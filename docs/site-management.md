# サイト運用・管理基準

この文書は、`kuraberu-products` を継続的に管理するための基準です。新規記事、既存記事の更新、UI改善、検証、本番反映を同じ品質基準で扱います。

## 管理方針

- サイト全体の目的は、商品やサービスを公式情報と確認状況を分けて比べること
- カテゴリは限定しない。育児用品の記事が多くても、サイトを育児用品専門サイトとは扱わない
- ユーザーに指摘されたページだけでなく、全記事・共通コンポーネント・一覧・メタデータを横断して確認する
- 変更は「依頼された箇所が変わったか」だけで完了にせず、既存ページの情報・リンク・構造化データ・モバイル表示を確認する
- 未確認の数値、価格、在庫、レビュー数、体験談を推測して掲載しない
- SNSの感想は参考情報として扱い、比較の根拠はメーカー等の公式情報に限定する

## 記事管理

### 新規記事

1. `docs/article-backlog.md` と調査メモを確認する
2. 比較対象、型番、公式URL、比較軸を公式サイトで再確認する
3. 記事メタデータ、商品画像、FAQ、購入リンク、情報源、変更履歴を同時に登録する
4. 既存の比較ページ標準構成を使う
5. 公式確認日と購入リンク確認日を記録する
6. ブランチ → PR → CI → マージ → production build → Direct Upload → 公開確認の順で進める
7. バックログを同じ変更で更新する

### 既存記事

- すべての記事を定期的に巡回し、共通構成から外れていないか確認する
- 共通レイアウトの変更は、原則として全記事へ適用する
- 商品固有の比較データ、公式URL、購入リンク、FAQ、SNS参考情報は記事ごとに保持する
- 商品情報の確認日が古い記事は、公式ページを再確認してから更新する
- 画像の欠落、見切れ、リンク切れ、重複CTA、空のセクションを修正する
- 過去記事を更新した場合は `modifiedAt` と `changeLog` を更新する

## 標準記事レイアウト

水筒記事を基準に、記事詳細は次の順序を基本とする。

1. メタ情報・タイトル
2. 比較ヒーロー（左右の商品画像、商品名、短い判断軸、公式・購入リンク）
3. ページ内ナビゲーション
4. 主要差分（値・差分の強調）
5. 「どっち向き？」判断ガイド
6. 比較後の購入カード（商品ごとに1回）
7. 詳細仕様（必要に応じて折りたたみ）
8. 公式情報・比較表
9. SNSでの感想（参考情報。投稿0件の場合はセクションごと非表示）
10. FAQ
11. 購入前に確認するページ
12. 記事末尾の購入カード、更新履歴、情報源、免責

記事固有の情報量によって一部を省略する場合も、理由なく別構成へ戻さない。共通UIは `src/components/ArticleComparisonV2.astro` と関連コンポーネントを正本とする。

## UI改善

- 見た目の改善は、色、余白、文字サイズ、画像比率、CTAの位置、モバイル幅をまとめて確認する
- A/B記号だけに頼らず、商品名と商品画像を前面に出す
- 差分は羅列せず、判断に使う値を強調する
- CTAは広告であることを隠さず、購入リンクと公式リンクを混同させない
- 変更後はデスクトップと390px前後のモバイル幅で、実際の生成HTML・ブラウザ表示を確認する
- 共通CSSの変更は、トップ・記事一覧・全記事への影響を確認する

## 定期巡回

本番確認では最低限、次を巡回する。

- トップ、記事一覧、全記事詳細
- 画像の読み込みとアスペクト比
- h1の重複、目次リンク、FAQの開閉
- 公式リンク、購入リンク、SNS埋め込み
- canonical、robots、sitemap、Article/FAQ JSON-LD
- 390px前後での横スクロール・文字のはみ出し・CTAの押しやすさ
- Consoleエラーと外部埋め込みの失敗

## リリース基準

- `DEPLOYMENT_ENV=preview pnpm verify` が全PASS
- production環境変数を読み込んだ `DEPLOYMENT_ENV=production pnpm build` が成功
- Cloudflare実測に合わせ、`kuraberu-products` Pagesへ `--branch main` でDirect Uploadする
- Deployment一覧で `Environment: Production`、`Branch: main`、対象コミットを確認する
- 本番URLと全記事URLがHTTP 200であることを確認する
- 生成HTMLに変更内容が反映されていることを確認する
- 完了報告では、未確認事項やローカル環境由来の制約を分離して記載する

## 変更単位

- 無関係な変更を同じPRへ混ぜない
- default branchへ直接pushしない
- 他担当の未コミット変更を上書きしない
- 本番反映はGitマージと別工程として扱う
- 秘密情報、APIキー、トークン、広告ID、鍵の値をログ・PR・文書へ書かない
